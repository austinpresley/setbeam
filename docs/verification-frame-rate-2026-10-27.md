# Frame-rate verification

Date: 2026-10-27. Version 0.2.0, build 15. Austin requested selectable FPS, including 1 fps for Capture One still-image review, with image detail taking priority over motion.

## Behavior

Advanced has Viewer frame rate beside Viewer picture, plus Screen capture frame rate when This Mac's screen is selected. Both settings persist independently and default to matching the source/display. Choices are 1, 5, 10, 15, 24, 25, 30, and 60 fps. Viewer changes preserve local monitoring, dimensions, bitrate allowance, the server, and the viewing identity. A screen-rate change restarts the selected screen capture and any live audience publisher while preserving an existing holding publisher. Hold remains silent, and relaunch remains private.

The viewer encoder selects frames by presentation timestamp before encoding, rather than depending on nominal RTSP frame-rate metadata. It keeps at most one frame per rounded time bucket and never synthesizes extra frames from a slower source. The bundled sample now uses the same audience encode as other sources. The build script checks for and bundles FFmpeg's select filter; no installed runtime dependency is added.

## Failures found during implementation

- The first complete FPS probe passed 1 fps at unchanged 1280 by 720 dimensions, 24 fps local monitoring, 5 fps output, a 14-second watchdog check, and audio-bearing Hold/Resume. Its slower-network-input check failed with `Could not find codec parameters for stream 0 (Video: h264, none): unspecified size` and `dimensions not set`. A focused low-rate input test reproduced this failure. The original 500 ms analysis window could end before the next 1 fps picture. Raising it to two seconds fixed source acquisition. Audience acquisition exposed the same short-window issue, and streams with missing timing metadata also waited for FPS or initial-DTS probes. Those probes are now bounded independently of cadence.
- Early cadence measurements included an untimed first RTSP picture or an initial RTP clock adjustment. One reported `Expected 5.0 fps on live, decoded 4.7485595803167175 fps with largest gap 0.38003299999999995`. Another rejected exactly two seconds due to floating-point representation. A relative-time interval also ended with too few valid timestamps after Resume. The probes now save decoded timing JSON under ignored `build/probe` and count selected video packets. The FPS probe skips two initial clock samples. The format probe measures steady cadence after two seconds and excludes the closing codec reorder tail, where stopping a finite packet read can omit B-picture reference packets. Its 2% cadence requirement and the strict no-audio gap limits remain unchanged; the new FPS probe allows 3% for rates that do not divide the source cadence evenly. The sample-loop gap expectation is described below.
- The first native 1 fps screen run stalled before a picture, and another run eventually accumulated enough pending data to close the input. The screen writer only retried a partly written frame on the next capture tick. A large encoded frame exceeded the pipe's capacity, so 1 fps could not drain it promptly. `VideoPipeWriter` now drains on pipe writability, cancels idle notifications, and keeps the existing 8 MiB bound. Its regression test sends one 512 KiB frame and requires byte-for-byte completion without another capture tick. A blocked/oversized write still closes its owned pipe once.
- A higher viewer limit on an already-1-fps input still produced `frame=0` while audio progress advanced. FFmpeg's automatic frame-threaded decoder buffered enough pictures to exceed the publisher watchdog. The audience decoder now uses two slice threads, and the native decoder uses the same mode. The focused audio-bearing 1 fps input/republish test passes after this correction. Actual timestamps, rather than nominal RTSP FPS, drive frame selection. Native frame-duration measurement now accepts the small interval jitter above one second that occurs with 1 fps display capture.
- An overlapping app build/runtime verification hit `Killed: 9` at `Vendor/bin/mediamtx --version` while a helper was overwritten in place. Runtime builds now retain identical MediaMTX bytes and replace rebuilt executables through a new inode. Native QA runs from an immutable copied bundle.
- Disabling initial-DTS discovery on the external stream-copy input caused a real regression in 60 fps H.264 with B pictures: timestamps repeatedly paired a 33.3 ms gap with an approximately 11 microsecond step, despite averaging 60 fps. That input now retains FFmpeg's DTS discovery. The external 1 fps input test and the full HEVC/H.264 passthrough/audience format probe both pass with the correction. Only the owned no-B-frame screen pipe and decoder paths bypass initial-DTS discovery.
- The packaged full run subsequently reached a 24 fps sample assertion: `expected 24.0 fps, measured 23.809621244729797, largest frame interval 0.06298900000000018 seconds`. This was initially attributed to clock alignment, but a direct file-only loop reproduced it without Setbeam or RTSP. Copying Demo.mp4 video with its AAC decoded to Opus produced video timestamps 7.958333333333333 then 8.021321614583334 at the eight-second loop boundary, a 62.988281 ms interval. AAC's 1024-sample priming contributes 21.333333 ms. Matching the source correctly retains this interval. The audio-bearing Demo expectation now allows one frame plus that known padding and 1 ms of timestamp rounding; other format fixtures keep their existing limits. Both final packaged format and FPS probes pass after this correction.

## Native and browser evidence

The focused saved-settings, display-rate cap, native freshness, and pipe-writer checks pass. Native UI selection of Viewer frame rate at 1 fps passed. Against the first packaged candidate, a Chromium browser decoded five 1280 by 720 frames in 5.079 seconds while continuously showing Live feed. Native monitoring retained 24 fps. Hold detached and muted playback, Resume decoded four frames in 4.006 seconds on the same page, and Stop detached playback while native monitoring continued. These results precede the final low-rate acquisition and pipe fixes; final packaged checks follow.

The combined candidate captured the actual 1920 by 1080 display at 1 fps. Native telemetry recorded four advancing frames across 4.000089 presentation seconds; after the frame-duration jitter correction it reported 0.999767 fps. Chromium decoded five 1920 by 1080 frames in 5.0039 seconds, with Live feed and no active audio track. Under Hold, changing screen capture from 1 to 5 fps retained the exact holding publisher and media-server processes. Native playback reached 5 fps, and Resume kept viewers at their separately selected 1 fps, decoding five frames in 5.0046 seconds on the same link. Stop detached/muted viewer media and left fresh native monitoring. Normal Quit removed all 11 recorded app/helper processes.

A separate non-integration preferences suite exercised actual Advanced Save with both rates at 1 fps. After normal Quit and cold relaunch, the same confirmed display restored with advancing native playback, both saved rates at 1 fps, and sharing/Hold off. All seven private-monitoring app/helper processes exited on Quit. No production preferences, Wi-Fi settings, or hardware session was operated.

## Final automated and packaged checks

`scripts/check.sh` against the final app's bundled helpers/fixtures passed 107 Swift tests, 18 viewer checks, file/RTSP native-preview bridge checks, and the full media, receiver-recovery, and safe-source-switching probes. Its format stage stopped at the sample-loop expectation recorded above. After correcting only the probe expectation, focused repeats using those same packaged helpers/fixtures passed the complete format probe and the FPS probe. No assertion for the real B-picture timestamp regression was removed.

The FPS probe decoded approximately 1 fps and 5 fps at unchanged 1280×720 dimensions, retained 24 fps local monitoring, stayed healthy across the 14-second watchdog check without a publisher revision, retained audio through live FPS/bitrate changes, preserved silent Hold and the viewing credential, kept an already-1-fps source at 1 fps under a higher viewer limit, restored Match source, and verified Stop/owned-process cleanup. The format probe preserved source codecs, dimensions, and 24/30/60 fps cadence, produced browser-compatible H.264 without B frames, retained the server/holding publisher through format changes, and verified one upstream reception.

Strict recursive signatures, system-only dependencies, all six viewer assets, bundled source/build records, and the frozen source/test manifest pass. The final app remains an ad-hoc signed Apple Silicon developer preview.

All seven owned app/helper processes exited on Quit. The archive contains only the app, finished build notes, and source/test manifest.
