# S-006 local address for viewers

Austin asked for a readable viewing address in place of the IP-only link and for a Settings field to customize it. Setbeam now publishes `setbeam.local`, or a name the operator chooses, for the viewing address while sharing. The name works only on the local network and needs no internet service. It is not a permanent link. Copy Link, the QR codes, the IP address link, the private per-session code, and optional viewer approval all remain. Claude Opus 5.5 implemented Build 23 with high effort, and GPT-6.1 Sol approved it with high reasoning effort in one review round.

## Design

- **Mechanism.** `LocalAddressPublisher` (`Sources/SetbeamCore/LocalAddress.swift`) asks the system DNS-SD responder, mDNSResponder, for one IPv4 address record: `DNSServiceCreateConnection`, then `DNSServiceRegisterRecord` with `kDNSServiceFlagsUnique`, the selected viewing interface's index, and a 120 s TTL, attached to a private serial queue. It needs no administrator rights. Setbeam does not rename the Mac, change DNS or network settings, or contact any outside service. The custom name is a real record: the system resolver, `curl`, and a browser on this Mac reached the gateway through it.
- **Conflicts.** The responder probes before answering. In testing, a conflict arrived both ways. A this-Mac-only registration was refused at once with `-65548` (`kDNSServiceErr_NameConflict`). A network registration was refused in the callback 0.3 to 2.6 s later. Per `dns_sd.h`, "name conflicts occurring for records registered via this call must be handled by the client in the callback", so Setbeam tries `name-2` through `name-20` and then reports the name in use. RFC 6762 §9 suggests that numbering, and it requires a host to give up a name when a conflict appears later. A later conflict after the name was active gets the same handling. A new viewing address keeps the name already held, so links already sent keep working. A new operator name starts over from the plain name. A responder failure or missing interface retries every 5 s.
- **Lifetime.** Setbeam publishes the name only while sharing on a network viewers can join. It deallocates the DNS-SD connection on its own queue, as `dns_sd.h` requires, when you stop sharing, sharing fails to start, a new source session resets the gateway, the network falls back to this Mac only, you turn the option off, or you quit. Stop Sharing still rotates the private code. A restarted session can reuse the name, but the old link stays expired.
- **What changes in a link.** Only the host. The port and the `/s/<private code>/` path stay the same. The gateway still binds only the selected IP address, so admission, approval, and the presence channel's `Origin == "http://" + Host` check work unchanged at either host. `config.json` still returns the numeric WHEP URL, so playback never depends on name resolution.
- **Invitations.** Copy viewing link uses the name once the responder reports it active. Until then it copies the IP address link. The join sheet shows the name in use and its state, plus Copy IP address link. Join codes in the panel, sheet, and setup check keep the IP address. Scanning needs no reading, and the IP link works on devices that cannot open `.local` names. The QR panel adds the name as one caption line under Copy viewing link (orange when renamed or unavailable), and the button's context menu has Copy IP Address Link.
- **Settings.** Advanced (⌘,) and Viewing network… in the gear menu open Viewer network. It now has Offer a local address (on by default) and a Local address field followed by `.local`. Setbeam ignores a trailing `.local`, lowercases input, and accepts letters, numbers, and inner hyphens, up to 40 characters. An invalid name shows an inline reason and disables Save, and an invalid saved preference falls back to `setbeam`. One status line shows the effective state: off, used while sharing, checking, active, in use with the numbered name, or unavailable with the IP address in use. If you change the name while sharing, Settings warns that viewers who opened the current name need the new link.
- **Words.** The glossary term is "Local address" (`CONTEXT.md`), not hostname, domain, or Bonjour name. Status prose uses non-breaking hyphens so `stage-a-2.local` never wraps at a hyphen.
- **Not done.** Typing a link by hand is still impractical because the private code is 64 hex characters. The local address makes the host readable and lets a copied link survive a DHCP change during a session. It does not shorten the code. A shorter or typeable code needs a separate decision, since it would weaken the code or overlap the candidate session password (S-004). The browser help and expired pages are unchanged. The expired page still carries no session data.

## Limitations

- **One Mac, no second device.** Every check ran on this Mac. The collision used a second registrant on this Mac with another address, not a second Mac, and no phone, tablet, Windows, Android, or second laptop opened the name. Whether a device resolves `.local` names, whether a network passes multicast, and any local network permission prompts on those devices remain open manual checks (S-006 [manual]).
- **Local network privacy.** The Apple TN3179 page could not be read; the fetch returned only its title. The app already declares `NSLocalNetworkUsageDescription`. Registration and resolution worked in the QA app, but QA captured only Setbeam's windows, so it could not observe system prompts. This Mac had already run Setbeam.
- **Stale caches.** After Stop, a rename, or Quit, this Mac kept answering from the record cached on its second interface for 30 to 128 s, up to the 120 s TTL plus the 5 s polling interval. The responder removed its own record at once. Other devices should drop the name when they receive the goodbye packet (RFC 6762 §10.1). Any that miss it can resolve the old name until the TTL ends. The old name still points only at this Mac, and the old code is already expired at Stop.
- **Shared names.** RFC 6762 does not count identical address data as a conflict, so two Setbeam sessions on one Mac and address share one name. Their ports and codes differ, so both links work.
- **Address changes.** A DHCP address change was tested with unit tests and the probe's address-change step, not with a real lease change. An open page fetches its own resources through the name, but WHEP uses the IP address, so playback after a lease change still depends on the existing reconnect path.
- **Unrelated failures.** The intermittent preview-bridge assertion above remains in unchanged code.

## Sources

- Apple mDNSResponder `dns_sd.h`, https://github.com/apple-oss-distributions/mDNSResponder/blob/main/mDNSShared/dns_sd.h: `DNSServiceRegisterRecord` (client-side conflict handling, interface index, unique flag), `DNSServiceCreateConnection` and `DNSServiceRefDeallocate` (deregistration), and `DNSServiceSetDispatchQueue` (deallocate on the same queue).
- RFC 6762, https://www.rfc-editor.org/rfc/rfc6762: §8.1 probing, §9 conflict resolution and renaming, identical data not conflicting, and §10 TTLs and goodbye packets.
- The Apple DNSServiceRegisterRecord and TN3179 pages returned titles only and were not used as sources.
